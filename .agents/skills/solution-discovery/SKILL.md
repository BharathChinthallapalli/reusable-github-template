# Discover the outcome and the smallest useful proof

Start with the user's task and existing project evidence. Separate the requested
feature or technology from the outcome it should produce. Identify the affected
people, current workflow, concrete failure or friction, and the decision this work
must inform. Reuse supplied facts before asking questions; mark assumptions and
ask only when a missing answer materially changes the next step.

For a discovery or evaluation engagement, read
[discovery and proof](references/discovery-and-proof.md) and adapt the
[solution brief](assets/solution-brief.md). Capture baseline evidence, constraints,
representative cases, measurable criteria, and bounded time or cost. Unknown
thresholds remain unresolved rather than being filled with invented targets.

Choose a demonstration, feasibility spike, or proof of value according to the
uncertainty. A demonstration illustrates a flow; feasibility checks whether a
mechanism works; a proof of value measures whether the outcome improves. State
which one was performed. Use [bounded experiments](../bounded-experiments/SKILL.md)
when executing repeated trials and [solution architecture](../solution-architecture/SKILL.md)
when a material design decision is needed.

For an implementation request, continue into the authorized smallest working
slice and meaningful verification. Record observed results and limitations;
use pass, fail, or inconclusive against the agreed criteria. Carry unresolved
production work and ownership into
[operational readiness](../operational-readiness/SKILL.md) when handing off a
workload. A successful demo does not establish readiness or new authority.
