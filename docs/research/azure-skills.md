# Azure Skills research for template expansion

Reviewed 9 September 2026. Repository pinned to `d4259f09db8f5631dce643427f0a55619b3f854f`; tree `bfe3c6a579a09ae4071baf95b6b2d82239fb6ad1`. This is research, not adoption of upstream instructions. No upstream code, cloud command, installation, provider, or MCP server was executed.

## Coverage and exact packaging

The complete recursive tree contains 2,522 entries and reports `truncated: false`. Canonical `skills/` has 925 files. The Azure plugin's 925 corresponding skill files have identical blob hashes: there is no content difference between these two copies at this revision. Each contains 38 `SKILL.md` files; this includes nested phase documents, so 38 is not a count of independently discoverable host skills. The canonical tree has 28 first-level skill families. The separate `azure-kusto-graph-skills` plugin adds three distinct skill families. There are no native `.agent.md` files or `agents/` definitions in the enumerated tree.

All 41 distinct entrypoint bodies were retrieved. All families were screened through entrypoint metadata, routing, and section inventories. Detailed body review concentrated on readiness, prepare, validation, deployment, resource discovery/visualization, diagnostics, cost, data and AI service routing, upgrades, and consumer packaging. Long specialist entrypoints were screened rather than reviewed line by line. [The source ledger](azure-skills-coverage.json) records those levels; fetching is not represented as a complete implementation review. Selected deeper files include the validation shell driver, readiness verdict logic, four-dimensional architecture rubric, handoff, Foundry validation rules/report workflow, tracing, evaluation datasets, and evaluation orchestration. The tree and original retrieved bodies are preserved separately as reproducible research inputs.

The root and packaged `.mcp.json` both declare only Azure via `npx -y @azure/mcp@latest server start`. The README also advertises Foundry MCP. Therefore an installation must inspect actual host tools; this source snapshot does not establish that Foundry MCP is wired. The README names `azure-rbac` and `azure-hosted-copilot-sdk`, which are not first-level canonical skill families at this revision. Foundry contains an RBAC sub-workflow. The two marketplace manifests include the second Kusto graph plugin, while `apm.yml` lists only the Azure package. Avoid treating the marketing list, one manifest, or a `SKILL.md` count as full consumer coverage.

## Recommended implementation

The current template has 24 skills and 10 agents, but no Azure task skill. Its Azure guide covers delivery identity, OIDC, environment scope, artifact identity, and rollback. Preserve that useful guidance and add executable-by-the-host procedures with explicit input/output evidence.

## Challenges to adoption

1. **Routing consistency:** `azure-prepare` frontmatter restricts use to azd, while its body broadly routes new/modified apps and offers several recipes. Do not reproduce this conflict or force an existing app to adopt azd.
2. **Enforcement versus instructions:** the validation shell script records the caller-provided completed step and emits a next action. It does not independently execute checks or prove success. Keep actual evidence distinct from a status field or design seal.
3. **Evidence vocabulary:** prereq build inspection can issue PASS without a build run. Our record should say static inspection passed and build unverified. A permission error or truncated inventory cannot mean no resources exist.
4. **Autonomy:** upstream frequently demands a fresh approval despite earlier task authorization, even before ordinary source edits or tests. Do not copy these process constraints; honor active task authorization and ask only when a concrete consequential action exceeds it.
5. **Least necessary dependencies:** no need to embed 925 vendor reference files, all cloud specialties, telemetry hooks, `@latest` MCP startup, subscriptions, or installed providers into every generated repository.
6. **Quality criteria must follow requirements:** the architecture rubric prescribes zone redundancy, GRS, monitoring, and private networking broadly. Apply measured reliability/data residency/security requirements and service constraints instead of universally provisioning expensive infrastructure.
7. **No unverified performance claims:** the gateway skill claims 60–80% semantic-cache savings and suggests raising token limits or lowering thresholds for failures. Do not import these as defaults; measure cache correctness and costs, isolate tenants, and diagnose throttling before changing controls.
8. **Test coverage:** the visible workflows build/deploy the documentation site and create sync releases. They do not establish skill-routing, real cloud deployment, or native host behavior. No upstream scripts were run during this review.

## Current primary documentation checks

- Azure MCP requires an enabled host connection and suitable identity/RBAC; installed skills are guidance rather than live account access. A local MCP server is a developer integration, not automatically a production application backend. [Microsoft Azure MCP overview](https://learn.microsoft.com/en-us/azure/developer/azure-mcp-server/overview).
- Azure Resource Graph queries have bounded result pages. Inventory procedures must inspect truncation/continuation and use stable ordering before claiming completeness. [Microsoft Resource Graph data handling](https://learn.microsoft.com/en-us/azure/governance/resource-graph/concepts/work-with-data).
- Cost reporting must preserve the selected scope, date range, currency, and actual/amortized interpretation rather than treating a catalog estimate as a bill. [Microsoft Cost Analysis](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/quick-acm-cost-analysis).
- Bicep what-if previews potential changes and has documented limitations; it is neither a deployment nor end-to-end application verification. [Microsoft Bicep what-if](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/deploy-what-if).

## Deferred domain implementations

AKS cluster creation/Automatic migration, GPU model serving, VM/VMSS capacity reservations, cross-cloud migration scripts, service-specific Redis/Functions migration, dedicated ADX/IRQL graphs, Entra Agent ID provisioning, Fine-Tuning SFT/DPO/RFT, voice/WebSocket hosting and model capacity deployment should remain discoverable source routes until a consuming project needs them. Their useful general contracts still belong in the architecture, identity, operations, evaluation and delivery procedures. A deferral is not missing research and is not a claim the template implements those workloads.
