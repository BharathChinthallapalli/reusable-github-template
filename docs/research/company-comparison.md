# Company repository patterns reviewed

Research date: 9 September 2026. These are first-party public examples, not a ranking or evidence that a pattern is deployed throughout each company. Repository pages and selected actual files were inspected. GitHub page snapshots sometimes had different crawl dates; the more recently fetched archive banner takes precedence over an older root-page label.

| Example | What it actually is | Observed evidence | Adopt for this template | Avoid copying blindly |
|---|---|---|---|---|
| [GitHub: typescript-action](https://github.com/actions/typescript-action) | GitHub Actions team's public template for building a TypeScript action | Root contains a Node version file, lockfile, tests, action metadata and CODEOWNERS. README explicitly tells consumers to replace/remove CODEOWNERS. [CI](https://github.com/actions/typescript-action/blob/main/.github/workflows/ci.yml) uses read-only contents permission, `npm ci`, format/lint/tests and a local action test. | Working checks, deterministic installation, explicit runtime, ownership personalization. | Action bundling and committed distribution files belong to action publishing, not every application. This sample uses major action tags; prefer current GitHub hardening guidance for the new template's action pinning. |
| [Microsoft: python-package-template](https://github.com/microsoft/python-package-template) | Public Python package template | `src`, `tests`, devcontainer and `pyproject.toml` centralize the package. [Dependabot](https://github.com/microsoft/python-package-template/blob/main/.github/dependabot.yml) covers both pip and Actions, with an upstream person's reviewer name. [Sync configuration](https://github.com/microsoft/python-package-template/blob/main/.github/template-sync.yml) lists selected files and exclusions. | Separate shared repository conventions from a language profile; dependency maintenance must include CI dependencies; record template provenance. | The upstream reviewer, Microsoft support/reporting contacts, overlapping linters and its 100% coverage requirement are project choices. Whole-file synchronization of customized README, license or project metadata can destroy project-specific decisions. |
| [GitHub: .github](https://github.com/github/.github) | Organization community defaults; not an application template | Root holds community documents. [SECURITY.md](https://github.com/github/.github/blob/main/SECURITY.md) sends vulnerabilities through private coordinated disclosure, asks for reproduction and affected revision, and distinguishes its bounty scope. | A defined confidential reporting path with the information needed to investigate; explain organization defaults separately from per-repository files. | Copying GitHub's contacts, bounty terms or corporate policy into an unrelated company repository. A file is documentation, not proof that platform controls are configured. |
| [Vercel: nextjs-postgres-nextauth-tailwindcss-template](https://github.com/vercel/nextjs-postgres-nextauth-tailwindcss-template) | Public application starter/template for an admin dashboard | App Router code, Postgres/Auth.js integration, pnpm lockfile and [`.env.example`](https://github.com/vercel/nextjs-postgres-nextauth-tailwindcss-template/blob/main/.env.example). README provides setup and local run commands and advertises Next.js 15. | Clear environment variable inventory, lockfile and short reproducible quickstart. | This is an application choice, not enterprise governance. Do not treat the framework version advertised in an existing starter as the latest release, or carry over Vercel, database and identity dependencies into every repository. |
| [Azure: azure-search-openai-demo](https://github.com/Azure-Samples/azure-search-openai-demo) | Public runnable RAG sample and azd blueprint; the page's repository type is ordinary Public | Separate `app`, `infra`, `evals`, `tests`, docs and scripts; `azure.yaml`; [AGENTS.md](https://github.com/Azure-Samples/azure-search-openai-demo/blob/main/AGENTS.md). README distinguishes demonstration from production and links a [productionization guide](https://github.com/Azure-Samples/azure-search-openai-demo/blob/main/docs/productionizing.md). | Keep infrastructure and application concerns distinct; AI projects need evaluations in addition to software tests; document local workflows and production gaps. | The sample's full retrieval/cloud stack, demo defaults and claims of production readiness. A tested generic template cannot establish that its future applications are secure or production-ready. |
| [Azure: todo-nodejs-mongo](https://github.com/Azure-Samples/todo-nodejs-mongo) | Historical public application template; [fresh workflow-directory view](https://github.com/Azure-Samples/todo-nodejs-mongo/tree/main/.github/workflows) reports archived 4 September 2026 | `src`, `infra`, tests, devcontainer and [azure.yaml](https://github.com/Azure-Samples/todo-nodejs-mongo/blob/main/azure.yaml). The azd manifest declares web and API services and maps infrastructure outputs into frontend build configuration. | Explicit source/infra boundary and documented configuration handoff as architectural patterns. | Do not recommend it as a current maintained dependency baseline. Do not import its application-specific services or deployment hooks into the core. |
| [Google: .github](https://github.com/google/.github) | Historical organization defaults; archived 18 May 2026 | Root contains conduct, contribution and security files. [SECURITY.md](https://github.com/google/.github/blob/master/SECURITY.md) centralizes vulnerability intake and describes coordination. | A consistent organization-level reporting destination and an explicit owner. | Archived status means it is a historical example, not the current recommended baseline. Google's response commitments, CLA and contacts cannot be inherited by another company. |

## Synthesis for the reusable template

These are design recommendations inferred from the comparison, not claims made by the companies:

1. Build a small language-neutral core that works immediately: README, contribution and security guidance, issue/PR forms, owner configuration, repository checks and dependency maintenance for Actions.
2. Keep Python, Node/TypeScript, Azure infrastructure and AI evaluation conventions in explicit optional profiles. A company's sample application is not a universally appropriate architecture.
3. Provide a deterministic initialization command to replace project name, owner/team, support and vulnerability contacts, and remove upstream identity. Fail clearly on unresolved required fields.
4. Separate repository content from GitHub settings. Explain which protections require repository or organization administration, and avoid a claim that files alone enabled them.
5. Make onboarding honest: a template check is not an application test; a sample deployment is not a production readiness assessment; a stale official starter is not evidence for the latest runtime.
6. Preserve a dated research record and template version. Updates should arrive as reviewable changes, especially for security defaults, rather than overwrite customized files.

This research is original paraphrase. No upstream code, policies, licenses, logos, contact details or CLA text was copied into the proposed template.
