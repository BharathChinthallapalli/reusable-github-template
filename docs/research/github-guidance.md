# GitHub template guidance verified 2026-09-09

This is an implementation research note. Recommendations below are our synthesis, not a claim that any one company uses this exact baseline. Public official documentation and first-party action repositories were read live.

## Core design

Use a small, stack-neutral repository template, a separate administrator setup checklist, and optional stack/deployment extensions. Distinguish project files from GitHub settings: committing a JSON ruleset or CODEOWNERS does not by itself enforce required reviews. Keep a working baseline CI check with a stable name; activate stronger gates after checking ownership, team capacity, repository plan, and the first successful run.

Git LFS content cannot be included. Generated branches have unrelated histories. | Default-branch-only generation is appropriate. Do not present template regeneration as upstream synchronization. | Merge queue | Required Actions checks need the separate `merge_group` event when merge queue is used. | Include `merge_group: {types: [checks_requested]}` for future compatibility, without enabling a merge queue automatically. Treat centralized public policy as an optional organization choice. | Dependabot | Configure `.github/dependabot.yml` with `package-ecosystem: github-actions`, `directory: /`, and a schedule to update action and reusable-workflow references. | Weekly version updates are a useful neutral default. ## Actions security baseline

Set `permissions: contents: read`, elevate permissions only in jobs requiring them, use full upstream commit SHAs, and automate reviewed updates. Avoid privileged `pull_request_target` or `workflow_run` execution of untrusted code. Pass untrusted context through quoted environment variables, not inline script interpolation. Prefer cloud OIDC with scoped short-lived credentials when deployment is added. Use GitHub-hosted runners for the default baseline. Crucial limitation: GitHub's current documentation says Dependabot vulnerability alerts do not cover SHA-pinned Actions, so version-update PRs and upstream release/advisory monitoring remain necessary. [GitHub secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use).

Checkout v7 adds default refusal to check out untrusted fork code under privileged triggers. Leave that protection enabled; `persist-credentials: false` is suitable when the job does not push. Node 24-based action versions require an updated runner; checkout documents minimum v2.327.1, with v2.329.0 required for authenticated git commands from Docker container actions. [Checkout README](https://github.com/actions/checkout).

Setup-python v7 uses ESM; its v6 runtime change requires runner v2.327.1 or newer. Specify `python-version` or `python-version-file`; relying on runner PATH makes interpreter selection unstable. Do not enable dependency caching when the baseline has no package manifest to hash. [Setup-python README](https://github.com/actions/setup-python).

## Proposed administrator baseline

Our recommendation: require PRs, one independent approval for team-managed projects, resolved conversations, a stable CI check, and prohibit force pushes/deletion of the default branch. Enable owner approvals after replacing placeholder owners with actual authorized identities. Keep a documented emergency bypass controlled by repository/organization policy. A single-maintainer project needs an explicit different review policy; otherwise the template can create an impossible approval gate. Treat paid scanning, release attestations, deployment environments, and cloud authentication as optional additions with named owners and prerequisites.

Do not automatically claim production readiness, compliance certification, tested GitHub-hosted execution, or inheritance of repository secrets, environments, permissions, and settings from the template.
